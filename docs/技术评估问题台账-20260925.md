## 1. P0 问题（6 项，按风险排序）

### P0-1 SSH 服务器主机键裸信任（TOFU 未接）　`✅ 已修复 f5cd3dc`

- **类别**：安全 / 设计承诺未兑现。
- **问题**：管理面探测与工具面连接池两处 `check_server_key` 均无条件返回 `Ok(true)`，无 known_hosts / TOFU 指纹比对。代码注释自认「TOFU 工具面切片接入」但未兑现；`server-hosting-design.md` 通篇也未把主机键校验列入 DoD。
- **影响**：Agent 经 `host__exec` 持有可执行任意命令的 SSH 通道，中间人替换服务器键 = 完全控制远端。与 HostAuthz 审批/审计的完备度形成反差。
- **证据**：`host::transport::ProbeHandler::check_server_key`（基线 host/transport.rs:19-29）、`host::pool::PoolHandler::check_server_key`（host/pool.rs:23-33）——两处均为 `Ok(true)`（已人工抽查复核）。
- **建议动作**：首连记指纹入 `server_host` 表 → 后连比对 → 变更时告警/阻断（可加「信任新指纹」审批卡）。russh 的 `Handler::check_server_key` 已暴露 `PublicKey`，工作量小。
- **DoD**：①指纹落库；②换键阻断且有审计记录；③管理面 test_connection 与工具面池共用同一校验。

### P0-2 host 域双零测试覆盖　`✅ 单测已修 fa7d799（L2 V 用例已入库，跑批证据待生成）`

- **类别**：测试。
- **问题**：host/ 全部 11 文件 0 个 Rust 单测；L2 评测 `CASES`（73 条）中无任何 `host__*` 前缀用例。而下列恰是易测纯函数：`host::policy` 路径归一化（`normalize_posix`/`check_path`）、`host::exec::build_remote_command`（单引号包裹 + sudo 包装，基线 host/exec.rs:28-39）、`host::authz` 424 行判定链、`host::credential::encrypt_payload/decrypt_payload`（基线 host/credential.rs:86-109）。
- **影响**：设计文档 §13 的 9 条 HostAuthz 验收项目前只能人工验证；「对标 Xshell」对外叙事前这是门槛项。
- **建议动作**：①纯函数单测一批（authz 判定链 × 信号矩阵、build_remote_command、policy 路径闸、credential round-trip）；②L2 补 3-5 条 host 用例，必须含「越权命令被 HostAuthz 拦截」断言。
- **DoD**：host/ 有测试文件且 `cargo test` 全绿；L2 CASES 出现 host__* 并进 gate。

### P0-3 沙箱逃生阀无权限控制 + Bun 侧无网络守卫　`✅ 已修 133438f（快照审计+设置区块+口径明示；gate 断言留中期）`

- **类别**：安全。
- **问题**：①`WD_SANDBOX_FS=off` / `WD_SANDBOX_NET=on` 仅读进程环境变量即关闭守卫，无审批、无审计记录——能改 App 环境的任何路径都可静默摘除防线。②Bun 侧 guard.js（基线 bun_manager.rs:130-190）只拦 `node:fs`，**无网络守卫**（mamba_manager.rs:154-156 自认「由观测层兜底」），不遵守代理 env 的 fetch 库可穿透。③观测层 `sandbox_audit::scan_script` 是关键词级静态扫描且 observe-only（sandbox_audit.rs:11、138）。
- **证据**：`mamba_manager::fs_block_enabled`（基线 :148-152）、net 放行（:138-144）、sitecustomize 守卫体（:176-346）、超时强杀（:453-479，已落地）。
- **建议动作**：①逃生阀改动写审计日志 + 设置页显式开关（含默认值与风险提示）；②Bun 网络守卫（--preload 同款 socket patch）或产品口径明示「Node 沙箱不承诺网络隔离」；③中期：escape 阀纳入启动时安全配置快照，进 release gate 断言。
- **DoD**：关守卫必有痕迹（日志/审计）；Bun 网络口径二选一落地。

### P0-4 取消链路两个洞　`✅ 已修复 5820ffd`

- **类别**：正确性 / 成本。
- **洞一（无取消感知）**：非流式 `agent::runtime::call_llm`（基线 agent/core/runtime.rs:1772-1776）签名无 cancel 参数——它是 **intent / planner / round_compactor / squad_orchestrator / pipeline 兜底 / forced_memory_settle 六条链路的公共底座**。用户在规划/压缩阶段点「停止」，最长白等 180s 超时窗且照常计费。对照流式侧已做对：`call_llm_stream_once`（:2095-2438）取消与 chunk 等待并发 select（约 :2255-2280），停止秒级生效；`call_llm_stream` 重试对「取消」直接透传不重试（:2047-2048）。
- **洞二（启动窗口吞取消）**：`run_task` 开头无条件复位 `cancel_flag`/`cancel_requested`（基线 :224-225），而抢锁 `try_acquire_run_lock`（commands.rs:161-167）到真正执行之间隔着异步 `load_config`（commands.rs:169-186）——该窗口内的「停止」被静默吞掉。
- **建议动作**：①`call_llm` 加 `cancel: Option<&Arc<AtomicBool>>`（默认 None 兼容存量调用点），在限流等待与响应等待两处检查；②复位前检查 `cancel_requested`，或把复位挪到抢锁成功后第一个 cancel 检查点之后。
- **DoD**：意图/规划阶段点停止 ≤3s 内出终态；停止不再产生该轮 LLM 计费尾单。

### P0-5 std Mutex 中毒级联　`✅ 已修复 c1df99e（34 处全清）`

- **类别**：健壮性。
- **问题**：请求路径约 40 处 `lock().unwrap()`（events.rs:79/106/227 的 `RUN_TRACES`、`agent/hitl/recovery.rs:144-209`、`plan_approval.rs:65-115`、`agent/core/runtime.rs:154/179/202` 的 tasks 锁等），唯一抗中毒写法只在 `llm_rate_limit_wait`（runtime.rs:1748 `unwrap_or_else(|e| e.into_inner())`）。任一处持锁 panic → 中毒 → 事件推送/审批/恢复/tasks 注册表全链路级联 panic。
- **建议动作**：机械替换为 `lock().unwrap_or_else(|e| e.into_inner())`（std Mutex 中毒后数据仍可安全续用，好过全崩）。半天工作量。
- **DoD**：`grep -rn "lock().unwrap()" src-tauri/src` 请求路径清零（测试代码不强制）。

### P0-6 无 CI，质量保障依赖人的自觉　`✅ 已建 70da998（gitee 不自动触发，见文件头三条出路）`

- **类别**：工程。
- **问题**：无 `.github/`、无 GitLab CI、无 Husky。release_gate.mjs 已具备 exit-code 挂 CI 条件（Harness 复评 :19 自述）但从未接入；93 个 Rust 单测只能手动 `cargo test`；typecheck 也不强制。

- **DoD**：主干 CI 绿灯为发布必要条件（与《发布门禁流程》衔接）。
