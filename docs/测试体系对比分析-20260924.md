# 测试体系对比分析：single-agent-capability vs l2_eval_harness（2026-09-24）

> 背景：`docs/single-agent-capability/`（另一 Agent 生成的单 Agent 能力测评套件设计稿）与本仓库
> `docs/skills/workduo-mcp/scripts/l2_eval_harness.mjs`（44+ 用例实战体系）的系统性对照。
> 目的：吸收对方长处完善自有方案，而非重复造轮子。

## 一、两套体系的本质差异

| 维度 | single-agent-capability（对方） | l2_eval_harness（本仓库） |
|---|---|---|
| **切分视角** | 引擎内部链路（intent/planner/pipeline/verifier/recovery/compactor 逐模块） | 业务场景与用户可感知行为（爬取/ETL/全栈/记忆/`.wd_mem`） |
| **判定方式** | 五维 0-5 人工评分（rubric 锚点+硬扣分+加权） | 客观自动化（终态/产物达成/resolved% 外层 pytest/gate 断言） |
| **执行状态** | **设计稿**（README 承诺的 run_capability_suite.mjs 缺失，未跑过） | **实战**（50+ commit 证据链，两轮重复性验证） |
| **负向测试** | ✅ 有（PL-3/PL-4 契约拒绝、D4 越界删除、D5-2 弱验收被拒） | ⚠️ 薄（几乎全是正向） |
| **链路断言** | ✅ trace 事件级（无 plan_generated、工具序列反模式、sensitive 留痕） | ⚠️ 只到结果层（status/产物），事件证据未结构化 |
| **成本断言** | ✅ D7-3 token 预算（prompt_tokens < 8k 阈值） | 🟢 今天起步（score 成本观测区，无阈值断言） |

## 三、已落地的吸收改动（本轮）

1. **通用信号层**：`runOneCase` 从 trace events 提取 `rec.signals = {hasPlanGenerated, planSteps, toolCalls[], writeCount, sensitiveCount, errorCount}`——任何用例从此都能做链路断言（不只 H 系列）。
2. **H 系列 6 用例**（scene H / phase 7）：H-M1 快路径、H-M2 灰色地带、H-M3 token 预算、H-M4 PathGuard 拒绝、H-M5 敏感留痕、H-M6 越界 delete。
3. **noWorkspace 支持**：CASES 可声明 `noWorkspace: true`（SIMPLE_CHAT 类用例不绑工作空间，测真实快路径）。

## 四、对方有但**不吸收**的（含理由）

| 项 | 理由 |
|---|---|
| 五维人工评分 rubric 作为主判定 | 与「客观自动化」路线冲突——人工评分留作 gate 之外的评审辅助，不进自动化判定 |
| 按引擎模块逐个建套件 | 我的业务场景体系已覆盖等价行为（如 D6 恢复门禁 = F-1/F-4/F-6，D8 隔离 = per-run trace + F-12 清扫），重复建设无增益 |
| 22 用例一次性平铺 | 场景有主次；我按业务风险排批次（P0/P1/P2 → C → G），收敛更快 |

## 五、遗留动作

- ⏳ H-M7/H-M8（PL 契约拒绝、SK 启停/导出导入）：MCP 直测（P2-3 同款内联验证模式），不依赖 agent run。
- ⏳ H 系列跑完后：把 signals 断言结果写回评分卡（引擎链路维度）。
- ⏳ 五维 rubric 的「人工评分点」清单可导出为 TEST-REPORT 附表，供评审会用（不影响自动化判定）。
