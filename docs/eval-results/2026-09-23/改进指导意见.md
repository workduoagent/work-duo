# WorkDuo L2 测评 — 产品改进指导意见（执行版）

> 2026-09-23 · 基于 34 用例 / 8 故障注入 / 13 并发组实测  
> 目标读者：产品 + 引擎负责人  
> 写法：每个问题 = 用户体感 → 证据 → 根因（文件:行）→ 具体改法 → 验收标准

---

## 总判断（只说三句）

1. **地基是好的**：不会永久挂死、并发不崩、锁能放、数据能清。高可用达到可内测水平。
2. **真正挡住「日常工作 + 写完整项目」的是同一件事：10 分钟 run 预算不够，且失败后不告诉你发生了什么。**  
   本轮 12/34 用例（35%）都是被 600s 墙钟杀掉的，不是模型不会做。
3. **改进不要摊开做 10 条**。按下面 **P0 → P1 → P2** 做完 P0+P1，场景 A/B 的通过率预计从 ~50% 产物达成提到 ~80%+。

# P0-1｜Run 预算 600s 不够用 —— 当前第一杀手

## 用户体感

> 「我让它搭一个带登录的全栈项目，转了 10 分钟，最后报『运行总时长超时，已强制终止』。  
> 界面上一片空白，我不知道它写了什么、还差什么、该不该重来。」

对用户来说这不是「慢」，是 **任务被系统掐死**。重跑一次还是 10 分钟，再掐死。产品不可用。

## 实测证据

| 指标 | 数值 |
|---|---|
| 被 600s 强杀的用例 | **12 个**（A-M2/A-M8/B-M3/B-M5/A-H1/H3/H6/B-H1/H2/H4/H6/H7） |
| 场景 B 高等难度产物达成 | **14%**（基本全灭） |
| 串行贴边案例 | A-M2 串行 473s 才 done（还缺产物）→ 并发下必炸 |
| 日志原文 | `运行总时长超时（600s），已强制终止以防任务永不结束` |

共性结论（已扩样）：**不是 flake**。只要是「多文件项目 / 多源数据 / Skill+KB 全链路」且并发 ≥2，几乎必撞墙。

## 根因（代码）

`src-tauri/src/agent/runtime.rs:1585`

```rust
const DEFAULT_RUN_MAX_SECS: u64 = 600;
```

`src-tauri/src/agent/commands.rs:192-208`（`run_agent_task`）与 `298-323`（`run_task_ex`）：

```rust
let run_limit = crate::agent::runtime::run_wall_clock_limit();
match tokio::time::timeout(run_limit, rt.run_task(...)).await {
    Ok(()) => {}
    Err(_) => {
        // 只 emit 一句话，不回写已产物、不回写进行到哪一步
        emit_task_error(&app, "运行总时长超时（600s），已强制终止...");
    }
}
```

三层超时设计里，第③层「run 总墙钟」把第①层（单次 LLM 180s）还没来得及暴露的「多步正常累积」也当成异常杀了。  
注释里写的场景是「本地模型 420s+ 仍未终态」——那是防挂死的兜底，**不该兼做业务 SLA**。

## 具体改法（按这个做，不要发挥）

### 改法 A（推荐，一次到位）：预算分级 + 超时可续跑

1. **默认值上调**
   - `DEFAULT_RUN_MAX_SECS`: `600` → **`1800`**（30 分钟）
   - 保留 `WD_RUN_MAX_SECS` 环境变量覆盖（已存在，`runtime.rs:1588`）
2. **按 intent 分级**（读 `intent.intent_type`，`runtime.rs:341` 已有）：
   | intent | 默认预算 |
   |---|---|
   | SIMPLE_CHAT | 120s |
   | COMPOSITE_TASK | **1800s** |
3. **超时不再「一刀切杀完」**，改为：
   - 调用 `tokio::select!` 同时监听 `cancel_flag` 与 wall clock
   - 超时：**停止发起新步骤**，等当前工具调用收尾（≤30s），然后进入「预算收尾」
   - 收尾必须写回：① `reply` 摘要 ② 已写文件列表 ③ `error_code = "run_budget_exhausted"`（与真挂死区分）

### 改法 B（若不想动默认值，至少做这个）

- 在 MCP `agent_run_task` 增加可选入参 `timeoutSec`（覆盖本次 run 预算）
- SKILL 写明：**全栈/多文件任务必须传 `timeoutSec >= 1200`**

### 不要做的事

- 不要把 600s 改成「无限」——挂死兜底必须留。
- 不要只改文档不改默认值——用户不会读文档。

## 验收标准

| 用例 | 现状 | 改后必须 |
|---|---|---|
| B-H1 全栈+JWT+Docker | error@600s | **done**，产物≥3/4，墙钟 <1800s |
| B-H2 MCP 聚合器 | error@600s | **done**，能打到 18755 |
| A-H3 全链路 | error@600s | **done**，报告含引标 |
| 模拟挂死（WD_LLM_TIMEOUT 不返回） | — | 仍在 1800s 或调用级 180s 内到 error，**锁释放** |

改完 `src-tauri` **必须重启 WorkDuo** 才生效。

# P0-2｜失败后「空白结局」—— 用户无法决策

## 用户体感

> 「失败了就失败了，你好歹告诉我：写到哪一步了？磁盘上有什么？是我 prompt 问题还是系统问题？  
> 现在 reply 是空的，我看日志才知道被 600s 杀了。」

**空 reply = 产品在最关键时刻失声。** 用户只能瞎猜、重跑、流失。

## 实测证据

| 用例 | status | reply | 磁盘实际 | 用户看到 |
|---|---|---|---|---|
| A-M2@C-3 | error | **空** | 有 `news_raw.json` 94KB | 什么都没有？ |
| A-H1 | error | **空** | 有部分 wiki 数据 33% | 完全失败？ |
| F-7 无 workspace | done | **空** | 无文件 | 成功了但啥也没有？ |
| 12 个 600s 用例 | error | **空或不全** | 常有半成品 | 无法续跑 |

`agent_get_run_trace` 的 `reply_chars=0` 在 600s 被杀案例中反复出现（见 `docs/eval-results/2026-09-23/*.json`）。

## 根因（代码）

1. 超时路径只 `emit_task_error(message)`（`commands.rs:205-208` / `319-322`），**不调用** `events::append_reply`，也不扫描 workspace。
2. `emit_task_error`（`events.rs:473-475`）只发事件字符串，**不写进 run trace 的 `reply` 桶**。
3. 无 workspace 时 PathGuard 拒绝写文件，模型最终自然收束成空回复，系统侧无兜底说明（`F-7` 实测）。

## 具体改法

在 **所有非正常终态出口**（超时 / 取消 / PathGuard 拒绝 / 恢复放弃）统一走 `finalize_run_summary()`：

```rust
// 伪代码 —— 放 events.rs 或新 summary.rs
fn finalize_run_summary(app, cfg, reason: RunEndReason) {
    let files = list_workspace_files(cfg.workspace); // 相对路径 + size
    let steps = current_plan_progress();             // 第几步/共几步
    let text = format!(
        "## 任务未正常完成\n- 原因：{reason}\n- 进度：{steps}\n- 已写入文件（{n}）：\n{files}\n- 建议：{advice}",
    );
    append_reply(&text);           // 进 trace.reply，MCP/UI 都能看到
    emit_task_error(app, &reason.to_string());
}
```

`RunEndReason` 至少区分：

| reason | 文案（给用户看） | 建议动作 |
|---|---|---|
| `run_budget_exhausted` | 运行预算耗尽（非挂死） | 加大 timeout 或拆任务；产物见上表 |
| `cancelled_by_user` | 已被用户取消 | 产物保留；可续跑 |
| `path_guard_rejected` | 未绑定工作空间，文件写入被拒绝 | 传 workspace 后重试 |
| `llm_timeout` | 模型调用超时 | 换模型/重试 |
| `recovery_abandoned` | 步骤失败且选择跳过 | 见进度表 |

## 验收标准

- 任一 error/cancelled 用例，`agent_get_run_trace` 的 `reply` **非空**，且包含「原因 + 文件列表」。
- F-7（无 workspace）`reply` 明确含「工作空间」字样。
- 600s/1800s 超时用例 reply 含 `run_budget_exhausted` 与至少 1 个已写文件名（若有）。

# P1-1｜「给我一份 Excel/图表」不可靠 —— 场景 A 日常工作硬缺口

## 用户体感

> 「多源抓取做综述可以，一说要 market.xlsx 和走势图就翻车。  
> 有时抓了一堆 JSON，Excel 死活出不来；PNG 有时行有时不行。」

日常办公最高频产物就是 **xlsx / png / docx**。现在全靠模型手写二进制，等于碰运气。

## 实测证据

| 用例 | 要求 | 结果 | 实际磁盘 |
|---|---|---|---|
| A-M2 | `market.xlsx` + `price_trend.png` | status=done 但产物 **0%** | 只有 `news_raw.json/xml` |
| A-H2 | CSV+JSON+MD+**PNG** | 产物 **100%** | PNG 能出来 |
| A-M2 并发版 | 同上 | error@600s | 半成品 |

**结论**：数据抓取/清洗没问题；**xlsx 是稳定缺口**；png 靠 prompt 运气；两者叠加再加并发 = 必挂。

## 根因

- 原生工具面（native tools）无 `write_xlsx` / `write_chart`。
- 插件生态无官方模板；模型要自己拼 openpyxl/matplotlib 并写文件，Windows 路径 + 依赖 + 长代码 = 高失败率。
- SKILL 也未告诉 Agent「要 xlsx 就用某插件」。

## 具体改法（不改 Rust 也能先做一半）

### 立刻可做（纯 SKILL + 插件，无需重启）

在 `docs/skills/workduo-mcp/scripts/` 增加两个 **官方插件模板**，并写进 SKILL「产物约定」：

1. **`plugin.xlsx_writer.template.py`**（runtime=python）  
   - `run({ sheets: { sheetName: [[cell,...],...] }, outPath })`  
   - 用 `openpyxl` 写 xlsx；缺依赖走 Runner exit 42 自愈。
2. **`plugin.chart_png.template.py`**  
   - `run({ kind: 'line'|'bar', xs, ys, title, outPath })`  
   - `matplotlib` Agg 后端写 png。

SKILL 增加一节 **「产物契约」**：

> 用户要 `.xlsx` / 趋势图时：**禁止手写二进制**；必须 `plugin_upsert` 上述模板（或复用已绑定插件）→ `plugin_test` → 调用生成。  
> 输出路径必须是 workspace 相对路径，文件名与用户要求逐字一致。

### 可选增强（Rust，要重启）

- native 工具 `native__write_xlsx` / `native__render_chart`（内部调 Python），对用户「说什么出什么」。

## 验收标准

- 重跑 A-M2：`market.xlsx`（≥3 sheet）+ `price_trend.png` **都存在**，且 Excel 可打开。
- 连续 3 次 A-M2 变体，产物达成 **3/3**（不是碰运气）。

# P1-2｜取消 / 计划门禁语义不真 —— 信任问题

## 用户体感

> 「我点了停止，任务还在跑，token 还在扣。下次不敢点停止，只能干等。」  
> 「计划确认弹窗有时候根本不出来，接口还报错说没有运行中的任务。」

## 实测证据

| 注入 | 预期 | 实际 | 文件 |
|---|---|---|---|
| F-1 中途 `agent_cancel_task` | run → `cancelled` | 仍 **`done`**，3 个 slot 全 done | `fault-F-1.json` |
| F-4 `planAutoApproveMode=always` | 应挂起等 approve | 8s 后已 `done`；`submit_plan` 报 **「当前没有运行中的任务」** | `fault-F-4.json` |

## 根因（代码）

### 取消

`commands.rs:531-554` `cancel_agent_task` **只置位 `cancel_flag`**，注释写「最佳努力，下一轮边界感知」。

问题：
1. 无强制终止——当前 LLM 流式/工具调用可以跑完才停。
2. registry 终态在 `commands.rs:328-334` 只区分 `timed_out ? error : done`，**没有 `cancelled` 分支**——即使 flag 置位，最终也写成 `done`。
3. 用户无法区分「我取消了」和「它自己做完了」。

### 计划门禁

`runtime.rs:178`：

```rust
format!("智能体 {id} 当前没有运行中的任务（状态束已随上次任务回收）")
```

`submit_plan_decision`（`commands.rs:642`）经 `resolve_task_state` —— 任务结束后状态束已回收，调用方得到的是 **Err 字符串**，不是 `Ok(false)` / `no_pending_plan`。

短任务在 8s 内跑完 → 门禁从未暴露 → 外部 Agent 误以为要 approve → 吃 error。

## 具体改法

### 取消（必须改）

1. `cancel_agent_task` 置位后，**立即**  
   `emit_task_error` / 或新的 `emit_task_cancelled`，并在 registry 写 `"cancelled"`。
2. `commands.rs:330` 终态改为三态：
   ```rust
   rec.status = if cancelled { "cancelled" }
                else if timed_out { "error" }
                else { "done" };
   ```
3. MCP `agent_get_status` / `agent_wait_task` 对外暴露 `cancelled`（更新 SKILL 状态枚举）。
4. 取消后：停止写新文件（工具层查 `cancel_flag`），已写保留，`reply` 走 P0-2 的 `finalize_run_summary(reason=cancelled_by_user)`。

### 计划门禁

1. `resolve_task_state` 失败时，`submit_plan_decision` / `submit_approval` 返回  
   **`Ok(false)` + 结构化 body** `{ ok: false, code: "no_pending_plan" }`，**不要 Err 吓人**。
2. MCP 工具描述写明：`decision` 返回 `false` = 无挂起，属正常。
3. SKILL「流程 1.1」补一句：短任务可能直接 done，`submit_*` 收到 `no_pending_*` 应忽略而非重试。

## 验收标准

| 项 | 标准 |
|---|---|
| F-1 | victim run status=**`cancelled`**（不是 done）；其余 run 正常 done；锁释放 |
| F-4 | 无挂起时 `submit_plan_decision` → `no_pending_plan`（非 error 字符串） |
| UI | 点「停止」后 2s 内状态离开 running，token 停止增长 |

改 `src-tauri` **要重启**。
