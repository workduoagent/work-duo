## 🧹 Windows 逐字路径前缀 `\\?\` 的展示净化（00:3x，方案 A，未提交待验证）
- **用户疑问**：界面路径显示为 `\\?\E:\WorkDuoTest\palindrome.py`，正常应是 `E:\...`。
- **根因链路（已定位）**：
  1. 绑定工程目录时前端（`agent-project-mapper.ts:73`）调用 Rust `canonicalize_path`（`fs_helper.rs`）；
     Rust `std::fs::canonicalize()` 在 Windows 上**约定返回 `\\?\` 逐字前缀**（绕过 MAX_PATH 260），
     该串被存进工程 `rootPath`。
  2. 产物路径：`artifacts.rs::resolve_path` 用这个 rootPath 当 ws 拼绝对路径 → 带前缀。
  3. 工具结果：`native.rs` 各工具的 `abs` 也是 canonicalize 出来的 → 工具返回串带前缀
     （如「已写入 N 字节到 \\?\E:\...」），**模型把它原样写进回答正文**，于是正文里出现前缀。
- **方案选型**：A=显示层净化（前端，立即生效、覆盖历史数据、无需重启）；B=源头净化（Rust 工具结果/产物路径）。
  B 中的 `canonicalize_path` **不要顺手改**——它是工程去重的键，老库带前缀记录会与新记录对不上，
  可能凭空多出重复工程。本次先做 A。
- **实现**：新增 `src/utils/pathDisplay.ts`（`stripWinVerbatim` / `stripWinVerbatimInText`），
  接入展示收口点：`CiteAwareMarkdown`（助手正文）、`MarkdownRenderer`（正文/思考段）、
  `ArtifactGallery`（产物卡：名称/title/复制/打开）、`ToolResultView`（工具结果，统一收口）、
  `ToolStepCard`/`ToolStepLine`（调用参数）、工程名 tooltip（rootPath）。
- **铁律**：只净化**展示**；真正用于 I/O 的路径保留原样（超长路径仍需要 verbatim 前缀）。
- **验证**：tsc 0E；纯前端，**重载即可**看到效果（历史数据也修）。待用户确认后再提交。
- **🐛 一个任务弹 4~5 条完成通知（00:5x，用户实锤）——根因是 HMR 重复注册**：
  通知处理器注册在 chat.tsx **模块级**，而 Vite react-refresh 会热替换组件模块——
  开发期每改一次 chat.tsx，模块就重执行一次，`onRunTerminal`（Set 叠加式）就多挂一个
  处理器 → 一次 `agent-task-done` 触发 N 个处理器 → 弹 N 条通知。
  修：①`runtimeStore` 的终态处理器改 **Map 按 key 幂等替换**（`setTerminalHandler(key, cb)`）；
  ②事件桥的注册标记改挂 **globalThis**（`__wdRuntimeBridgeStarted`）而非模块级变量——
  HMR 热替换模块时模块作用域重建、模块级标记复位 → Tauri 监听也会被重复注册、
  每个事件被处理多次，globalThis 跨热更新存活。**经验：模块级「只注册一次」的标记，
  在 Vite 开发环境必须挂 globalThis，且注册 API 必须按 key 幂等替换。**
- **通知样式二改（用户反馈）**：去掉正文摘要（高度还是太高）→ 只留「任务已完成 + 会话名(24字截断)」；
  **duration=0 不自动消失，手动关闭**；加 `agent-task-notify` className + layout.scss 压低

- **➕ HITL 挂起提醒（01:0x，用户提议，未提交）**：授权/计划审批/方案选择/步骤恢复这类
  **阻塞态**事件，人不在对话页时任务会默默卡死，必须提醒到位。实现与完成通知同构：
  - `runtimeStore`：四个挂起事件到达时 `firePendingNotify(sessionId, event)`（带类别映射表）；
    **同会话同类只提醒一次**（`lastPendingKind` 去重，任务终态清除，新一轮可再提醒）；
    `setPendingNotifyHandler(key, cb)` 按 key 幂等注册（同款防 HMR 叠加）。
  - chat.tsx 模块级注册：没在看该会话（`chatViewSessionRef !== sessionId`）才弹
    warning 通知（琥珀色区别于完成的绿色）：「任务暂停：高危操作授权」+ 会话名 +

    antd 原地替换不叠加；duration=0 手动关闭；窗口失焦补系统通知。
  - 精准收起：①点开该会话（决策面板可见）→ `notification.destroy('pending-<sid>')`；
    ②提交决策挂起态解除 → 同样 destroy。注意本版 antd 实例类型是 `destroy(key?)` 而非 `close`。

- **🐛 挂起通知不弹（01:2x）——runtimeStore 被 HMR 重执行导致三连灾难，已根治**：
  开发期编辑 runtimeStore.ts → Vite 重执行该模块 → 模块作用域整体重建：
  ①运行态 Map 全丢；②Tauri 监听重复注册、每事件处理多次；③新旧两份注册表脱节
  （旧监听写旧状态、新代码读新状态）→ 事件流断裂 → **通知再也不弹**（真机实锤：
  日志 emit ok 但界面无通知）。
  修：**模块可变状态整体挂 globalThis**（`__wdRuntimeStore`：entries/subscribers/
  terminalHandlers/pendingHandlers/lastPendingKind/runningSessionId/runningAgentId/
  bridgeStarted），模块重执行时复用同一份状态与标记。此前只把 bridge 标记挂
  globalThis 是不够的——监听闭包引用的旧状态容器依旧和新的脱节。
  加诊断日志：`[runtime] pending notify`（handlers 数量）+ `[chat] pending notify handler`
  （viewing 与否），下次可直接定位断点。
  **经验（重要）：凡「模块级单例 + globalThis 标记」的模块，其全部可变状态都必须一并挂
  globalThis，否则 HMR 后新旧实例状态分裂。**
- **设计确认**：挂起提醒的触发条件是「没在看该会话」——正在看时决策面板就在眼前，
  不弹 toast（与完成通知同规则）。若用户在会话页内期待也弹，需单独再改。
