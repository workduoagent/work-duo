## 「网关/模型延迟定位」定性复核（2026-09-22 23:2x，代码研读）
- **结论：延迟本身不必改（非网关瓶颈）**。决定性推理：同一网关、同一任务、同一引擎下 DeepSeek-V4.1-Flash 最长静默 **6.7s** vs Qwen3.6 **105s**（15 倍差）——若为网关瓶颈则两者应同慢。故慢是**模型侧属性**，做「网关架构定位/重构」属错误归因，投入产出比低，**不建议立项**。
- **🔴 但代码研读挖出两个真缺陷（该项应拆分，不可直接删除）**：
  1. **真缺陷 A（支柱①，必须修）**：`runtime.rs:1516 call_llm` **完全没有 HTTP 超时**——`reqwest::Client::builder()`（:1533）未调 `.timeout()`，`req.send().await`（:1586）也无 timeout 包装。而 COMPOSITE 的 **planner（planner.rs:99）** 与**执行调用（pipeline.rs:1289，带 tools）** 都走 `call_llm`。→ 模型不返回即**无限等待**，这正是「永不终止 → future 永不 resolve → RunningGuard 永不 drop → **锁永占**」的**机制性根因**。修法＝加 180s 超时（与「失败收尾」第一层是同一处代码，应合并做）。
  2. **真缺陷 B（支柱③，值得做）**：COMPOSITE 规划/执行是**非流式**（`stream: false`，runtime.rs:1541）；只有 SIMPLE_CHAT（runtime.rs:812）与 exec 层（pipeline.rs:1120）走 `call_llm_stream`。故 Qwen3.6 那 75s/105s 期间**零输出**——这正是「慢和死在观测上无法区分」的根源。修法分两级：**轻（推荐先做）**= 等待心跳事件（每 Ns emit 已等待时长，低风险立刻补观测洞）；**中**= planner 改流式（拼完整再解析，消除最长黑屏）；执行调用带 tools 流式解析复杂，建议先用心跳覆盖。
- **排期建议**：① 先做「失败收尾」（含给 `call_llm` 加超时，地基中的地基）；② 之后做心跳（观测闭环）；③ **不做**网关架构定位。原清单「网关/模型延迟定位」应改为：取消立项 + A 并入失败收尾 + B 单独立项归支柱③。
