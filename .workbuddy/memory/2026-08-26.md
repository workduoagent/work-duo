## 控制台警告：无法解析 '--foreground' 自定义属性
- 根因：`src/styles/root.css` 第 46/52/66/70 行在 `color-mix(in srgb, var(--foreground) X%, transparent)` 里**裸引用**了 Appica 的 CSS 变量。Appica 的 `@theme inline` 已经把裸变量桥接成了 Tailwind 颜色 token：`--color-foreground: var(--foreground)`（styles.css 第 32 行）。
- 修复：把 4 处 `var(--foreground)` 全部替换为 `var(--color-foreground)`，走 Tailwind 已注册 token，编译期解析、不会触发运行时警告。
- **经验：Appica 项目里凡是要在 `color-mix()` 或自定义 CSS 中引用语义色，一律用 `var(--color-xxx)`（带 `color-` 前缀），不要写 `var(--xxx)`。** 同样的规则适用于 `--background` / `--border` / `--muted` 等：未在 `@theme` 注册的裸变量在某些场景下会被浏览器报"无法解析"。

## ⚠️ 上条经验作废，改用「裸变量 + 项目内兜底」
- 上一轮把 `var(--foreground)` 改成 `var(--color-foreground)`，**仍然报"无法解析 '--color-foreground' 自定义属性"**。
- 真正的机制：Appica 的 `styles.css` 里 `--color-foreground: var(--foreground)` 是 `@theme inline` 里的**桥接声明**——它告诉 Tailwind v4 "这个 token 运行时再查 `--foreground`"，**而 `--foreground` 自己的值（`oklch(...)`）在 `:root, .light`（第 179 行）里给出**。结果就是 `--color-foreground` **本身在浏览器里也是"未解析"的**，最终值依然要查 `--foreground`。
- 真正会报"无法解析"的也不是浏览器，而是 **vite 7 + tailwindcss 4 默认走的 `lightningcss` 编译期校验**：它在处理 `color-mix(... var(--xxx) N%, transparent)` 时，会检查**自己当前可见的 CSS 范围**里 `--xxx` 是否已被声明；如果 import 顺序让它先看到用户 CSS、还没看到 Appica 的 `:root, .light` 块，就会报警告。
- **正确修法（`root.css` v2）**：
  1. 把 `var(--color-foreground)` 改回 `var(--foreground)`（这才是 Appica 真正给值的裸名）；
  2. 在项目自己的 `:root` 块显式声明 `--foreground: oklch(0.446 0.03 256.802);`，`.dark` 块声明 `--foreground: oklch(0.872 0.01 258.338);` 作为**编译期可见兜底**；
  3. 运行时 Appica 的 `:root, .light` / `.dark` 块位置靠后会自然覆盖这两个值，主题色不变。
- **新经验（覆盖上一条，收束为两条硬规则）**：
  1. **写 `color-mix()` 时，直接用 Appica 已注册的「带 `color-` 前缀」token**（`var(--color-foreground)` / `var(--color-border-muted)` / `var(--color-background-subtle)` 等）。这些在 `@theme inline` 里已桥接、build 产物可完整解析，不会报"无法解析"。**不要**写裸 `var(--foreground)`（dev 模式 lightningcss 顺序敏感，可能报"无法解析 '--foreground'"）。
  2. 「裸变量名 + `:root` 兜底」这条**撤销**：实测发现它会让 `--color-*` 链路在 dev 下仍被 lightnings 报；而且运行时 Appica 的 `:root,.light`/`.dark` 块位置靠后会覆盖兜底，反而让"兜底"显得多余。最终采用「`color-` 前缀 token + `@supports(color:color-mix(...))` 块包裹」写法（参考 layout.css），既稳又无需兜底声明。

## 主题开关第四轮：动画仍不生效的真凶 = 我加的 reduced-motion 守卫（重要教训）
- 用户反馈：切换不抖动了，但**滚动动画依然没实现**；并报 CSS 校验错误 `display: -ms-flexbox`（85行，"不匹配的属性值"）。
- **排查**：编译产物里 `transition: var(--circle-transition)` 与 `calc(100% - ...)` 都完好、结构正确 → 声明没问题。唯一能把全部过渡"掐死"的是我自己加的 `@media (prefers-reduced-motion: reduce){ ... transition: none !important }` 守卫。
- **根因**：用户 Windows 系统开了"减少动画"（设置→辅助功能→视觉效果→关闭"动画效果"时，`prefers-reduced-motion: reduce` 命中），守卫用 `!important` 把所有过渡强制 none → 切换变成"瞬时跳变"（正好对应"不抖动但无动画"）。参考稿本身没有此守卫、能正常动画。
- **修复**：① 删除 reduced-motion 守卫整块（用户明确要动画）；② 删 `display: -webkit-box; display: -ms-flexbox;`（过时厂商前缀，Chromium/WebView2 不需要），只留 `display: flex`，修复 lint 报错；③ 更新头注释说明不保留守卫的原因。
- **关键教训**：`prefers-reduced-motion` 只是媒体查询，**不会自动禁掉过渡**；只有 CSS 显式 `transition:none` 才会禁。给组件加 `transition:none !important` 的 reduced-motion 守卫要非常谨慎——会在用户系统开减少动画时把核心动画整个废掉。本项目（用户明确要动画）一律不加。注意：编译产物里仍有 Appica 骨架屏 `.skeleton-shimmer` 与路由淡入 `.page-transition` 的 reduced-motion 规则，与本开关无关。
- 校验：`tsc` EXIT 0；`vite build` EXIT 0；编译产物 `display:flex` 生效、过渡完好、无守卫、无 CSS 告警。
