## ✅ 修复：success_criteria 残缺导致恢复死循环（verifier 降级）

- 后端：①`types.rs::AgentRuntimeConfig` 加 `plan_auto_approve_mode: String`；②`plan_approval.rs` 加 `plan_requires_approval(plan)` 敏感词判定（命令执行/删除/系统路径/部署/DB写等，刻意不收 password/token 以免误伤「创建登录页」）；③`runtime.rs::run_task` 门禁前算 `auto_skip`（never=全跳/sensitive=!requires_approval 则跳/always=门禁），auto_skip 时 `emit_status`「自动放行」不挂起；④`commands.rs::load_config` 从 agent_info 读（默认 always）。
- DB：`init.sql` 加列 `plan_auto_approve_mode TEXT DEFAULT 'always'`；`updater.sql` 加 **v22** ALTER 补齐存量库。
- 前端：`database.d.ts`(行)/`core.d.ts`(`PlanApprovalMode` 类型 + AgentConfig/AgentUpsertInput 字段)/`agent-mapper.ts`(读+写+INSERT 三处)/`draft.ts`(类型+默认'always'+draftFromAgent+draftToInput)/`StepBasic.tsx`(智能体向导「计划审批」Segmented：总是审批/仅敏感任务/从不审批)。
- 验证：`npm run typecheck` 零错误（修 2 处：mapper 缺 `PlanApprovalMode` 导入、`AgentUpsertInput` 缺字段）。Rust `cargo check` + DB v22 迁移待用户本地。

## 🐞 修复：agent 保存报「20 values for 21 columns」（mapper INSERT 占位符漏一个）
- 现象：编辑智能体、计划审批选「仅敏感任务」保存 → `保存失败：error returned from database: (code: 1) 20 values for 21 columns`。
- 根因（上次 2b-3 allow 层加列的尾巴）：`agent-mapper.ts` 的 `upsertAgent` INSERT 列清单已含 21 列（含新列 `plan_auto_approve_mode`），参数数组也已是 21 个值，但 `VALUES (...)` 只写了 **20** 个 `?` → SQLite 报列/值数不匹配。这是典型的「改 DDL 后只补了列清单和参数、漏补 VALUES 占位符」错位漏改。
- 修复：`agent-mapper.ts:311` 的 `VALUES` 由 20 个 `?` 补到 **21** 个，与列清单、参数数组三要素完全对齐（`plan_auto_approve_mode` 位于 `memory_mode` 之后、`created_at` 之前，位置无串列）。
- 排查范围（按用户要求「查所有相关 mapper」）：①`grep INSERT INTO agent_info` 全项目仅 `agent-mapper.ts:307` 一处（该 upsert 同时负责新建+编辑保存）；②`scenario-mapper.ts` 仅引用 `agent_info.scenario` 做引用置空，不重建 agent_info 行，无碍；③Rust 侧只 `SELECT * FROM agent_info` 读配置，从不 INSERT，无需改。
- 验证：`tsc --noEmit`（受管 node）exit=0 零类型错误（SQL 占位符错位 tsc 不报，需人工核对三要素）。用户本地重跑 `npm run tauri`（HMR 即时生效）后复测保存。
- **教训红线**（用户强调，已写 MEMORY.md DDL 段）：任何 `ALTER TABLE ADD COLUMN` 之后，必须 grep 项目中所有 INSERT 该表的 mapper，逐一核对「列清单 / VALUES 占位符 / 参数数组」三者数量与顺序一致，防占位符漏写或位置串列（上次 `created_at` 被串填成 `off` 即同类错位）。

## 🚧 修复：2b-3 实测「步骤受阻·需决策」弹窗（planner target 垃圾路径导致校验恒失败）
- 现象：选「仅敏感任务」模式跑「新建登录页」，门禁自动放行（符合 allow 层预期，非 bug），但执行后弹「步骤受阻·需要你的决策」，原因「校验未通过（文件应存在且非空（任一）：\\?\E:\WorkDuoTest\generated_code_content）」。
- 根因：planner（小模型 gemma4:e4b）把 `success_criteria.target` 填成占位名 `generated_code_content`，根本没从用户 prompt 提取真实路径；`verifier.rs` 只认 planner 声明的 target → 该路径不存在 → 恒判未闭环 → 进恢复链路弹窗。与门禁无关（门禁本次本就不该弹，因为是 sensitive 模式低风险任务）。
- 用户澄清输入：实际提示词是 `/api/userinfo` + `src/views/Profile.tsx`（非此前误传的 /api/login + src/pages/Login.tsx）；据此撤回上一轮「接口被改」的误判（模型 summary 也是 /api/userinfo，二者一致）。
- **方案 A 落地（图驱动校验）**：校验器改为核验「本步工具实际写出的文件」而非仅 planner 声明 target。
  - `verifier.rs`：`check_one` 加 `extra: &[PathBuf]` 候选参数，`resolve_candidates` 结果追加 `extra`（7 个文件类分支全改 `let mut cands` + `cands.extend`）；`verify_task` 改两阶段——先仅按 planner target 校验，未命中再兜底核验 `actual_written`（工具真实写出文件），任一真实文件满足谓词即通过，并 `tracing::info` 记录兜底命中。
  - `pipeline.rs::run_subtask`：终态校验前用 `changed_files`（run_tool_calls_round 聚合的 write/edit/delete/move 实际路径，已解析绝对路径）构造 `actual_written` 传入 `verify_task`。复用既有 `changed_files`，零侵入 native.rs。
  - `graph.rs`：新增 `add_produced_files(task_node_id, files, workspace)`，把本步真实写出文件写图（FileRef 节点 + Produced 边），作为图驱动约束的权威产物来源（与 legacy `register_artifacts` 从 summary 抽取互补）；`pipeline.rs::run_pipeline` 成功闭环处调用（图在此处是 `&mut`，无借用冲突——run_subtask 不持 graph，故图写放在父层）。
- 设计取舍：`run_subtask` 不持有 `graph`（父层 `&mut`），把图直接传进原生工具会触发借用冲突，属大改且无法本地编译 → 选复用 `changed_files` 的轻量方案；真实写出路径即「将成 Produced 边」的同一数据，语义等价。把真实写出写进图（add_produced_files）补上图侧忠实度。
- 验证：沙箱 D: 盘未挂，Rust 需用户本地 `cargo check`（src-tauri/）+ 重启 `npm run tauri`。前端无改动。仅 Rust 改动，未跑 tsc（无关）。
- 仍存的次要质量问题（非本次阻塞，方案 B 范畴，未做）：plan 端路径漂移——用户要 `src/views/Profile.tsx`，模型可能写成 `src/views/Login/index.tsx`；fallback 以「实际写出文件」通过校验，但落盘路径与用户意图不符。如需强制，应在 planner 提示词做用户显式路径确定性提取兜底（正则 `写到\s+(\S+\.tsx)`）。
- 结论：2b-3 计划审批门禁本身已 ✅（always 模式真机验过）；本次弹窗是 2b-1/2b-2 恢复门禁被 planner 垃圾 target 误触发，方案 A 已消除该误触发。
