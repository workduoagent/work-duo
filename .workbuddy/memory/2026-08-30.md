## pdfjs-dist v4 worker 路径坑（运行时修复）

## 知识库建库报 "no column named logo"（存量库迁移遗漏）
- 现象：创建知识库报 `error returned from database: (code: 1) table knowledge_base has no column named logo`。
- 根因：`init.sql` 的 `knowledge_base` 建表**已含 `logo TEXT`**（第 212 行），但用户本地存量 `workduo.db` 是在 logo 列加入建表语句**之前**创建的；`CREATE TABLE IF NOT EXISTS` 对已有表不补列 → 实际表缺 logo，INSERT 含 logo 即报错。`knowledge-mapper.ts` 第 182 行 INSERT 含 logo（与 TS 类型 `KbListRow`/`KnowledgeBaseRow` 一致，代码侧无错）。
- 修复（走项目约定，非首启走 `updater.sql` 迁移）：在 `src/assets/sql/updater.sql` 追加 **v5** 块 `ALTER TABLE knowledge_base ADD COLUMN logo TEXT;`（带注释）。`SqlService.updateTables`（第 77 行）对 `duplicate column name` 安全跳过，幂等。
- 生效方式：重启 app（`npm run tauri` 或整窗 reload）使 `InitContext.initDB()` 重跑 `updateTables` 给存量库补列；热替换单模块不会重跑 initDB，须整窗重载/重启。
- 经验：**在 `init.sql` 给某表新增列时，必须同步在 `updater.sql` 追加 `ALTER TABLE ... ADD COLUMN`，否则已有用户库的表结构会落后于建表 DDL 而报 no such column**。Stage A 只改了 TS 类型 `KbListRow` + `knowledge-mapper` INSERT，漏了 updater.sql 迁移 → 本次补回。

## PDF 查看器崩溃修复：Rendered more hooks than during the previous render（13:55）
- 现象（重启后真报错，非 HMR 噪声）：进知识库打开 PDF 直接崩，报错 `Rendered more hooks than during the previous render`，栈顶 `defaultLayoutPlugin → useMemo` @ index.tsx。
- 根因（真实的 Rules of Hooks 违规）：PdfViewer 顶层 hook 顺序为 useMemo(url)/useEffect(revoke)/useState(mods)/useState(err)/useEffect(load)（共 5 个），随后在 `if(!mods) return 加载中` 提前返回；mods 加载完成后再渲染 JSX 并调用 `defaultLayoutPlugin()`，该函数内部用 `useMemo`（即第 6 个 hook）。于是「mods 未加载首帧（5 hook）」与「加载后（6 hook）」hook 数量不一致 → React 崩溃。本质是被提前 return 挡在了 hook 之前的 JSX 里调用了一个 hook 工厂。
- 修复（src/components/MultiFileViewer/index.tsx）：把真正渲染拆成 `PdfViewerInner`，外部 PdfViewer 只负责加载模块 + 提前返回；内层 PdfViewerInner 在顶层**无条件** `const layoutPlugin = defaultLayoutPlugin()`（defaultLayoutPlugin 必须作为 hook 在组件顶层调用，因内部用 useMemo），不再有提前 return 挡在它前面。新增 `PdfMods` 接口承载动态模块集合。
- 排查经验（强约束，可入规范）：**任何内部使用 hook 的工厂函数（如 react-pdf-viewer 的 defaultLayoutPlugin()），必须在组件顶层无条件调用，绝不能放在 early-return 之后的 JSX 里**；含动态 import 的查看器应拆「加载壳组件 + 渲染内组件」两层，确保 hook 数量恒定。已核对 ImageViewer/VideoViewer/AudioViewer/DocxViewer/XlsxViewer/MarkdownViewer/EpubViewer 的 hook 均在 early-return 之前，无同类问题。
- 校验：npm run typecheck EXIT 0。

## PDF 查看器 blob URL 失效修复（13:57）
- 现象（hook 修复后真报错）：PDF 能进渲染但报 `Failed to load resource: net::ERR_FILE_NOT_FOUND`，指向 `blob:http://localhost:1420/...` URL。
- 根因（与图片直显同类——blob URL 生命周期脆弱）：PdfViewer 原用 `useMemo` 创建 blob URL + 单独 `useEffect(() => () => URL.revokeObjectURL(url))` 仅负责 revoke。React 18 StrictMode(dev) 下组件会 mount→unmount(模拟)→mount：模拟卸载时 cleanup 已把 blob **revoke**，但 `useMemo` 在重挂时因 `[bytes]` 不变不重建 → 传给 @react-pdf-viewer 的 fileUrl 是个**已失效的 blob URL** → pdfjs 取文档即 ERR_FILE_NOT_FOUND。
- 修复（MultiFileViewer/index.tsx）：blob URL 改在 effect 内创建并 `useState` 承接，`return () => URL.revokeObjectURL(u)` 在同一 effect 内；这样 StrictMode 重挂会重建有效 URL。加载守卫改为 `if (!mods || !url) return 加载中`（url 为空时先不渲染内组件）。彻底规避「useMemo 创建 + 独立 effect revoke」在 StrictMode 下的失效窗口。
- 校验：npm run typecheck EXIT 0。
- 经验（强约束）：**在 React 18 StrictMode 下，需要 revoke 的 Object URL 一律用 effect 内创建 + 同 effect 内 revoke，禁止 useMemo 创建 + 独立 effect 仅 revoke**（后者在 dev 双挂载下必然失效）。图片直显此前已改用 base64 data URL 规避同类问题，PDF 因体积用 blob 但须套此模式。
