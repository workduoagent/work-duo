## #20260915003 真机点验发现死锁回归（已修复）
- 时间：2026-09-15。用户 `never`(从不审批+自动执行) 模式跑"读取不存在的 missing_file_xyz.txt"。
- 现象：日志 `全自动模式(never) 步骤 1/1 自动接管重试（带诊断回灌）` 后紧跟 `依赖死锁，中止……受阻步骤：1(status=retrying)`，无恢复弹窗、任务直接挂死。
- 根因：【我自己引入的回归】#003 把重试臂节点从 `pending` 改成置 `retrying` 后 `continue`；但 `graph.rs::topo_ready` 只把 `pending` 当就绪候选 → `retrying` 既不被主循环重新拾起、`session_all_completed` 又不为真 → 主循环顶部死锁检测器(pipeline.rs:185，`status ∉ {completed,skipped,obsolete}` 即判卡死) 把 `retrying` 误判为"无法解决的步骤依赖" → 直接 return 中止。所有重试路径(手动三臂 + never 自动)都踩同一坑。
- 修法：放宽 `graph.rs::topo_ready` 就绪判定为 `status ∈ {pending, retrying}`(依赖检查不变,retrying 前置必已闭环)；重试步回到主循环即被重新拾起→running 重跑，不再空就绪→死锁分支不触发。`blocked` 不受影响(置 blocked 后 recovery.wait() 阻塞不回主循环)。死锁检测器逻辑无需改。同步订正 pipeline.rs 两处过时注释(原写"改回 pending")。
- 通用教训（图驱动状态机铁律）：**调度器新增任何瞬态 status，必须同步加进 `topo_ready` 的就绪集(及 `session_all_completed` 的闭环集，若它算终态)，否则死锁检测器会把新态误判挂死**。改前务必 grep `topo_ready` / `session_all_completed` 的就绪/闭环候选集。
- 验证：`cargo check --lib` EXIT=0。跟踪文件 `#20260915003` 详情卡追加「回归修复」段；状态改「✅ 已实现+编译已验证；死锁回归已修复，待重启重测」。
