- 复核修正：走查称「绕过全部沙箱守卫」**表述过重**——实测 `run_script_with_selfheal:1234` 对两条通道都注入了沙箱双守卫（网络默认关+文件有界，NetPolicy::Blocked）。真实缺口是：① script_path 任意（仅 exists()）；② 脚本读取不受限且 stdout 回流渲染层——构成「读任意文件+沙箱内执行」原语。修复即针对这两点。

## 问题与影响

作为 Tauri command 暴露，script_path 前端直传仅 exists() 校验——无 PathGuard、无 allow_sandbox、无 RequireApproval。与受控入口 run_python_in_sandbox（走 with_sandbox_guards + PathGuard + 审批）是两个不同函数。叠加 CSP null，渲染层任意注入即可执行本机任意 Python/Node。

## 修复方案（v2 · 方案A，用户定案）

命令保留（前端零改造），内部补路径安全边界（fs_helper.rs）：

1. `allowed_script_roots(app)`：允许根 = 应用数据目录 + 资源目录（mamba/bun 管理资产）+ 全局工作空间（读 settings `workspace_path`，支持 $APPDATA 占位符）。
2. `ensure_script_path_in_roots(script, roots)`：canonicalize 后**组件级** `Path::starts_with` 比对（防 `base` vs `base_secret` 字符串前缀绕过，§1.8 同类问题预防）。
3. `run_python_script` / `run_node_script` 两个命令在 exists() 校验后调用上述边界；越界报错文案明确。
4. 运行时守卫（with_sandbox_guards + NetPolicy::Blocked）本就由 run_script_with_selfheal 统一注入，双通道一致，无需改动。

方案 B（删命令砍沙箱页功能）被否；方案 C（留无守卫特殊通道）不可行——渲染层无法证明 invoke 来自用户点击。
