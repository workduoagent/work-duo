## F024：localStorage 读写收敛 —— ✅ 实际已完成（此前误判）

### 核查结论

`safeParse` 7 处 → 1 处已完成；`lsList` / `lsSave` 共享实现**早已存在**（`src/core/mapper/localFallback.ts`）；
10 处 `lsRead` / `lsWrite` **全部已在调用共享实现**，每处函数体仅 1 行：

```ts
// src/core/mapper/agent-project-mapper.ts:46
function lsRead(): AgentProject[] {
  return lsList<AgentProject>(LS_PROJECT)   // ← 共享实现
}
function lsWrite(list: AgentProject[]): void {
  lsSave(LS_PROJECT, list)                 // ← 共享实现
}
```

实测：10 处全部命中 `lsList` / `lsSave`（`grep -A2 ... | grep -c` = 10）。

### 为什么这层包装**不该拆**

它不是重复代码，而是**必要的类型标注 + key 封装**：

- 类型安全：调用点写 `lsRead()` 直接得`AgentProject[]`，不必每次写 `lsList<AgentProject>(LS_PROJECT)`；
- key 封装：`LS_PROJECT` 是模块内常量，封装后 storage key 不会散落到业务代码。

拆掉反而是倒退（业务代码里要到处写 key，常量的封装意义就没了）。

### 全项目直调 localStorage 的仅剩 1 处（合理）

`src/core/mapper/config-mapper.ts:73/77` —— 该文件存的是 `Record<string, string>` 形态
（键值对字典），**不是数组**，`lsList`/`lsSave` 的 `T[]` 签名不适用。属正确保留。

### 对报告原节的修正

报告 §1.24 写「`lsRead`/`lsWrite` 的去重本轮主动放弃……命名不统一导致正则批量改写
引发连锁语法破坏（一度 80 error）」—— **该理由不成立**：实际命名很统一
（`lsRead` / `lsWrite` / `lsReadSessions` / `lsReadRounds` / `lsSave*`），
且这层包装本就不该拆。`bulkUpsert` 零调用问题亦已于 `db62e2a` 完成
（model-mapper 抽出 `MODEL_COLUMNS` 复用 `sqlUtils.bulkUpsert`，
加 `preserveColumns` 保住「更新不覆盖 created_at」语义，有专项回归）。

**⇒ F024 从残项清单移除。**

## F028：PathGuard 边界 —— ⚠️ 主项证伪，子项未做

### 主项：盘符相对路径逃逸 ——❌ 已证伪（误判）

报告称 `C:foo` 可逃逸。**Rust 实测证明不成立**：

- `Path::new("C:foo.txt").is_absolute()` 为 false（确实走 `ws.join` 分支）；
- 但 `Path::join` 在右侧含盘符前缀时会**丢弃左侧前缀**（Windows 语义），
  于是 `candidate` 仍是 `C:foo.txt` 而非 `D:\workspace\C:foo.txt`；
- `logical_normalize` 保留 Prefix 段，最终 `starts_with(ws)` 为 false → **被正确拒绝**。

未改生产代码，改为在 `agent/engine/tools.rs:410` 新增 `path_guard_tests`（4 项）固化为回归断言。

### 子项：symlink TOCTOU —— 🔴 真实遗留

`verify_real_path`（`tools.rs:306-307` 代码注释自认）：

- Unix：走 `/proc/self/fd/<fd>` 强保证，可捕获 symlink 替换；
- **Windows：无 `/proc/self/fd`，退化为对 `abs` 重新 canonicalize**
  ⇒ 存在「校验通过 → open 前 symlink 被替换」的 TOCTOU 窗口。

修法需引入 Windows `GetFinalPathNameByHandleW`，改动 Rust 边界原语，
**风险高于前三项**。

### 需用户决策

这个窗口在你的实际使用场景下是否可接受？若工作空间内不放symlink（Windows 需管理员
或开发者模式才能创建），风险有限，可判定为「刻意保留」并写明理由。
