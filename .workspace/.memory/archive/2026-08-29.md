## TopBar 返回上级时胶囊（高亮滑块）宽度闪动修复
- 现象：钻取二级（百宝箱）正常；点返回按钮后一级平铺，但选中项后面的彩色高亮药丸（`.app-nav-pills__thumb`）宽度/位置会「闪一下」瞬间跳变。
- 根因：`TopBar.tsx` 的逐帧跟踪 effect 原条件为 `drilledKey===null && exiting===null` 才 return，即只要 `drilledKey` 或 `exiting` 任一存在就 `setTracking(true)`。而 `data-tracking='true'` 的 CSS 关闭了 thumb 的 `transform/width` 过渡，改由 JS 逐帧测量驱动。返回时 `drilledKey` 已清空但 `exiting` 仍在播放，`selected` 瞬间从二级子项（窄）变回父级 `百宝箱`（宽），过渡被禁用 → 第一帧即从「窄+右」瞬跳「宽+左」= 闪动。进入二级时不闪，因父级 `百宝箱` 本就锚定在左、位置不变。
- 修复：effect 条件改为 `if (drilledKey === null) return`，即「返回上级（仅 exiting 播放）」不再开启跟踪，让 thumb 走 `.app-nav-pills[data-ready]` 的 0.5s 正常过渡平滑地从子级滑回父级；「进入二级」仍保留跟踪（父级锚定不动，避免拖影）。进入二级的瞬变维持现状（用户确认正常）。
- 校验：`npm run typecheck` EXIT 0。

## MCP 支持 streamableHttp 类型 + 新增导入功能
- 背景：用户问能否接入 `{"mcpServers":{"mineru":{"type":"streamableHttp","url":"https://mcp.mineru.net/mcp","env":{"MINERU_API_TOKEN":"..."}}}}` 这类 Server。结论：能。Rust 后端 `src-tauri/src/mcp.rs` 的 `sync_mcp_tools`/`call_mcp_tool` 已按 Streamable HTTP 实现（POST initialize→读 `mcp-session-id`→后续带会话 id）；只拒绝 STDIO，非 STDIO 一律 POST Streamable，故 `streamableHttp` 等价于现有 `HTTP（Streamable）` 选项。Mineru 文档确认 token 走 `Authorization: Bearer <token>`。
- 发现：此前 MCP 只有「批量导出」mcpServers.json，**没有导入**；表单协议下拉无 `streamableHttp` 字面量、无 `env` 字段。
- 用户选择「做导入+智能映射」：新建 `parseMcpServersJson(raw)`（src/core/file/mcp-file.ts）：type stdio→STDIO（command/args/env 进 properties）、sse→SSE、streamableHttp/http(s)/未知→HTTP；url→endpointUrl；远程服务 env 无子进程需转请求头——`*_TOKEN`/`*API_KEY`/`*API_TOKEN` 类 → `Authorization: Bearer <值>`（authType=API_KEY+authConfig 同步），其余 env 按同名 header 兜底；headers 字段直接并入；非法 mcpName 规整并告警；返回 `{items:McpInfo[], warnings}`。同时给 `mcpToServerConfig` 写出标准 `type` 字段（stdio/sse/streamableHttp）以闭环 round-trip。
- 新增 `McpImportModal.tsx` + `McpImportModal.scss`：粘贴/上传 .json → 解析 → 勾选列表（全选/计数/告警/协议·地址·含认证预览），确认回传选中 McpInfo[]。
- `mcp/index.tsx`：顶栏加「导入」按钮（Upload 图标，在「批量导出」前）→ `McpImportModal`；`handleImport` 逐个 `upsertMcp`，同名服务按现有 id 覆盖（幂等）。
- 注：浏览器 dev 回退走 `mcp-connection.ts` 的 fetch 探测（同样 POST+session id），Tauri 走 Rust。校验：`npm run typecheck` EXIT 0。
- **Mineru MCP 接入排障（实测）**：① `401 C1114 scope forbidden` 真因不是 token 域权限，而是导入解析把 `env.MINERU_API_TOKEN` 强制改成了 `Authorization: Bearer`，而 Mineru MCP 是以 `MINERU_API_TOKEN` **同名头**（原始值，无 Bearer）鉴权；用户手动改 `authConfig.key_name=MINERU_API_TOKEN` 后鉴权即过。② `406 Not Acceptable` 根因：用户在 `headers` 手填 `Accept: application/json`，合并时覆盖了协议必备 `Accept: application/json, text/event-stream`。
- 修复（3 处，`npm run typecheck` EXIT 0）：`mcp-file.ts` 的 `parseMcpServersJson` 改为 **env 一律同名头转发**（原始值）、token 类额外补 `Authorization: Bearer` 兜底、`authConfig.key_name` 改用 env 原名；`mcp-connection.ts` 的 `buildHeaders` 末尾强制 `Accept`/`Content-Type`；`src-tauri/src/mcp.rs` 的 `sync_mcp_tools`+`call_mcp_tool` 把 `JSON_RPC_HEADERS` 移到用户头/认证头**之后**插入（协议头最后生效）。⚠️ Rust 改动需 `npm run tauri` 重新编译后才生效（用户当时 dev 跑的是 Rust 后端）。
- **Mineru MCP 接入排障（续）**：`initialize` 过了但 `tools/list` 报 `error decoding response body`（即 `tools/list 响应解析失败`）。根因：上一步把 `Accept` 改成 `application/json, text/event-stream` 后，Mineru 改以 **SSE（text/event-stream）** 返回，`event: message\ndata: {...}` 流格式，而 `mcp.rs` 原先用 `tools_res.json()` 解析纯 JSON 失败。修复：新增 `parse_json_rpc_body()` 兼容纯 JSON 与 SSE（抽取 `data:` 行拼接解析），`sync_mcp_tools` 的 tools/list 改读 `.text()` 后走该函数并额外捕获 JSON-RPC 层 `error`；`call_mcp_tool` 的 `raw` 同样抽取 data 行输出整洁 JSON。`cargo check` + `npm run typecheck` 均 EXIT 0。Rust 改动需 `npm run tauri` 重编译生效。
