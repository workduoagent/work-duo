## 严重设计缺陷：计划/执行文件名自相矛盾 → 客观校验误判未闭环（用户贴 Agent.log 反馈）
- 现象：任务整体成功、产物齐全（实际落盘 `bnb_weekly_report.md`），但 step1/step2 校验报「文件应存在且非空：...bnb_weekly_price_data.csv/.bnb_weekly_summary_forecast.md：系统找不到指定的文件 (os error 2)」，步骤判失败。
- 根因（**非我本会话改动引入**）：`verifier.rs` 不在本会话 git diff 内（仅动了 pipeline/planner/types），校验逻辑未变。校验期望文件名来自 `task.success_criteria`，是**计划阶段 LLM（planner）声明**的产出；而执行阶段是另一个 LLM 调用驱动沙箱 python，实际写盘文件名由它自由决定（日志 line 796 `REPORT_OUT=...bnb_weekly_report.md` / 885 `[ok] saved`）。两处 LLM 对「文件名」自相矛盾。读 `pipeline.rs:run_subtask` 确认执行器 prompt（line 297）只给「步骤标题/详述/前序产物」，**从未把计划规定的输出文件名告知执行器** → 执行器自由命名 → 与校验期望对不上。
- 修复（`pipeline.rs:run_subtask`）：新增 `criteria_hint`，把 `task.success_criteria` 转成「本步骤成功判定的硬性产出要求（文件名/路径须一致，不要自行改名或合并）」注入子任务执行 prompt（插在「前序步骤已交付产物」与「请直接执行」之间）。把「计划—执行」绑定，让执行器写出的文件名与校验器检查的一致。`cargo check` 零警告。
- 关联：此缺陷与上一轮「步骤漏发 step_finished(true)」是**两个独立 bug**、表象都是「步骤红叉」；本次修复从根上消除计划/执行命名错位，是执行正确性层面的修复。
- 提醒：prompt 注入是原则性修复但非 100% 保证（LLM 仍可能不听话）。若复现，可再补「校验器对执行器实际产物做模糊匹配」安全网，但需权衡误收风险——暂不实施，留待真机验证。

## 优化4 · 零输出快速重试（call_llm_stream，闭环三优化剩余项）

- **诚实自评**：之前给的「预期 ~24 积分 / 总省 61%」**预测过于乐观**——把「零输出浪费消除」误等同于「全部浪费消除」。实际可消除的浪费只是其中一部分（🔴 5.68 + 优化2 ~5 + 缓存 5–8 = ~15–18 积分 ≈ 25–30%），已实测兑现 31.7%。
- **结论**：四优化合计 **31.7% 节省 + 零输出浪费彻底消除**，是真实收益。剩余 47.5% 的「输入大但输出小」是决策型调用的固有成本，没有合理优化空间。本次账单作为「四优化后实测基线」存档。
- **后续**：若想进一步压低总成本，唯一可挖的方向是 **缩短 LLM 决策型调用的输入**（更深度的上下文压缩，比如只保留最近 1 条 tool 结果或更激进摘要），但会牺牲 ReAct 多步推理上下文完整度——ROI 不明确，暂不实施。
