### ② 第二次运行点「停止」无效（脚本照跑到底）
- **根因（双重）**：
  1. `script_cancel.rs`的 `LAST_ID` **永不清空** —— `unregister_script_run` 只清注册表 `runs()`，没清 `LAST_ID`，留下陈旧 run_id；

- **修法**：`unregister_script_run` 同步清 `LAST_ID`（**仅当LAST_ID 指向被注销的 run 时才清**，避免注销旧 run 误清新 run）；前端改为**串行三步**：`const running = runScript(...)` → `void lastScriptRunId().then(setRunId)`（并发于结果渲染）→ `await running`。**不能简单写成 `await runScript()` 再取 id**（那会等到脚本跑完，「停止」按钮就废了）。

### 🔴 Rust 测试踩坑：全局静态状态被并发污染（新发现，铁律级）
- **现象**：新加的 `unregister_clears_last_id` 与既有 `unregister_prevents_leak` **失败**，报`left: Some("sbr_..._5") right: Some("sbr_..._2")`、`left: 3 right: 1`。
- **根因**：`RUNS` / `LAST_ID` 是**进程级静态**（`OnceLock<Mutex<..>>`），而 Rust `#[test]` 默认**多线程并行** ⇒ 用例之间互相注册/注销，全局状态互相污染。**注意：既有的 `unregister_prevents_leak` 本来也有此隐患，只是此前恰好没被触发。**
- **修法**：加 `static TEST_LOCK: Mutex<()>` + `fn lock()`，凡会 register/unregister/读活跃数的用例先`let _g = lock();`。
- **🔴 关键坑：锁不能跨 `.await`** —— `lock()` 是同步 `MutexGuard`，async 用例里跨 `.await` 持有会死锁（同线程其它用例等锁，而 await 在等 timer）。故两个 async 用例（`request_cancel_delivers_signal` / `runs_are_isolated`）改成**分段加锁**：同步段 `{ let _g = lock(); … }` 返回 `(id, sub)`，await 段不持锁，收尾再 `let _g = lock();`。
- **通用教训**：给进程级静态状态写测试，必须有全局测试锁 + 明确 async 用例的锁边界。这条与前端「memory 铁律」同源——**共享可变状态 + 并发 = 必须显式串行化**。

### 写测试踩坑（复现验证）
- **断言源码位置时不能直接用 `indexOf(fnName())`** —— 会匹配到**注释里**提到的旧写法，断言失效。必须用行级正则 `^(const\s+\w+\s*=\s*|void\s+)?fn\(` 精确匹配调用行。
- **源码是 CRLF**，`trim()` 不去`\r`，`endsWith('= runScript(')` 判断失效；须用正则匹配整行。
- `__dirname` 相对路径按**当前测试文件所在目录**算（`src/pages/squads-workspace/x.test.ts` → `join(__dirname, 'SquadDetailPage.tsx')`，不要多套一层）。
